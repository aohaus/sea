# 4. Adaptive Lesson Selection Rules

The planner is a deterministic, versioned function:

```
plan = planSession(profile, retentionState, contentBank, privateContext,
                   budgetSec, now, plannerVersion, seed)
```

The LLM may *generate* candidate items and write explanations; it never picks
what to study. Every planned item carries `plannerReasons` (rendered in
Japanese under 「なぜこの内容？」).

## 4.1 Session types and budgets

| Kind | Default budget | Composition target |
|------|----------------|--------------------|
| Weekday quick | 5 min (presets 3 / 5 / 10) | ≤ 50% due reviews, 1 focus KC in 1 scenario, ≤ 1 probe |
| Sunday review | 25 min | Week's material interleaved, speaking block (≥ 5 min), 2–4 probes, weekly report |
| Diagnostic | ≈ 8 min × 3 | doc 5 |
| Free practice | learner-chosen | same rules, no budget enforcement |

Time per item is estimated from the learner's own median by format
(prior: MCQ 8 s, cloze 15 s, translation 30 s, speaking 25 s + feedback).

## 4.2 Planning algorithm

1. **Budget.** `B = budgetSec × 0.9` (10% slack for feedback reading).
2. **Due reviews.** Items with `R(now) < 0.90`. Priority
   `= (0.90 − R) × importance`, importance = frequency × personal relevance.
   Fill up to 50% of B (Sunday: 60%). Overflow: keep the top by priority,
   reschedule the rest across the next 3 days (backlog smoothing; never more
   than 1.5× normal review load per day).
3. **Surprise probes.** With probability 0.6 on weekdays (1 item) and always
   on Sunday (2–4 items), pick from Fragile/Durable items or KCs with
   last exposure ≥ 7 days, `R(now) ≥ 0.85` (i.e. **not** already due), oldest
   gap first. Probes look identical to normal items; after answering, the UI
   reveals 「抜き打ち確認」 and what it measured. Cap: 15% of items.
4. **Focus KC selection.** Score every eligible KC (prerequisites with
   p̂ ≥ 0.7 or Unknown-but-probed):

   ```
   U(k) = 0.35·Gain(k) + 0.25·Relevance(k) + 0.20·InfoGain(k)
        + 0.10·Weakness(k) + 0.10·Staleness(k) − Fatigue(k)
   ```

   - `Gain`: expected improvement; highest when p̂ ∈ [0.55, 0.85]
     (desirable difficulty), low for mastered or far-too-hard KCs.
   - `Relevance`: overlap with active scenarios in the private profile and
     upcoming events (e.g. school term start, festival in ≤ 14 days).
   - `InfoGain`: expected σ² reduction — drives exploration of Unknown KCs
     (this is how missing data gets *measured* instead of assumed low).
   - `Weakness`: error-tagged KC from recent `response_graded.errors`.
   - `Fatigue`: penalty if the KC was the focus in the last 2 sessions or
     has a cramming flag (doc 3 §3.6).

   Weekday: top 1 KC. Sunday: top 2–3. Weights are config, tuned weekly.
5. **Scenario selection.** Among scenarios that exercise the focus KC,
   choose by `relevance × staleness`, never the same scenario three sessions
   in a row.
6. **Difficulty targeting.** Choose items whose predicted p is near:
   learn 0.75, review 0.85, stretch 0.60. Format ladder per KC:
   recognition (MCQ) → cued recall (cloze) → production (translate,
   dialogue) → speaking. Move up a rung after 2 first-try successes at
   p̂ ≥ 0.8; down after 2 failures.
7. **New-item cap.** ≤ 6 new memory items per weekday session, ≤ 12 Sunday;
   none if review backlog > 2 days' load.
8. **Ordering.** Warm-up (1 easy review) → interleave reviews and focus
   items (no two items of the same KC adjacent unless a worked example
   sequence) → probe in the middle → finish with a success-likely item.
9. **Content gaps.** If no item fits (KC × scenario × difficulty), request
   generation (§4.5); use the nearest existing item meanwhile.

## 4.3 In-session adaptation

- 3 consecutive failures ⇒ drop target p to 0.85 and insert a worked example.
- Response much faster than expected and correct ⇒ next item from one rung
  higher.
- Budget exhausted ⇒ finish current item, skip remaining; unplayed review
  items return to the queue (no penalty).
- Session abandoned ⇒ logged; never counted as failure of unseen items.

## 4.4 Pre-generation and offline

After each session and at 05:00 MYT, the server pre-plans the next weekday
and Sunday sessions and the PWA caches them (items + TTS audio). Plans are
re-validated on open; if stale (> 24 h or profile changed materially) the
client asks for a fresh plan when online, else uses the cached one.

## 4.5 Content generation rules

- Generated by LLM from templates: `(KC, scenario, register, format,
  target level)` → structured JSON validated by zod.
- Checks before acceptance: schema, lemma lexicon check, no Indonesian-only
  forms (e.g. reject *kamu tidak bisa*-style unless explicitly contrasted),
  both registers given where they differ, Japanese explanation ≤ 200 chars,
  answer variants list (e.g. *tak/tidak*, *nak/hendak*, *kat/di*).
- New items start `status: 'candidate'`, become `active` after first use
  without a flag; flagged ⇒ `retired`.
- Seed set (~300 items covering diagnostic and first 4 weeks) reviewed by a
  native speaker if available.

## 4.6 Weekly plan update (Sunday)

1. Engine computes the week's metrics (doc 3 §3.8, §3.10) into a JSON
   snapshot.
2. Planner proposes next week's focus: top KCs by `U(k)` over a 7-day
   horizon, scenario mix, target time, new-item rate (lower if durability
   < 0.75, higher if > 0.9 and backlog small).
3. LLM writes the Japanese narrative **only from that JSON** (numbers are
   inserted by template; the narrative is checked to contain no numbers not
   present in the snapshot).
4. Learner accepts or edits (e.g. "来週は病院の場面を増やす") ⇒
   `plan_accepted`; edits become relevance boosts.
